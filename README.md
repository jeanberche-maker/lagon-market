## Lot 11 — carte réelle (OpenStreetMap, sans clé API)

Le **Suivi** et les **Zones couvertes** s'affichent sur une vraie carte Leaflet + tuiles OpenStreetMap :

- **Suivi** : épingle 🏪 boutique → villa 🏠, tracé lagon du trajet, livreur 🛵 qui glisse le long du tracé (`interAlong`/`posToT`, mêmes 22 % → 88 % que le pin stylisé), badge ETA conservé au-dessus de la carte, livreur devient ✅ à la livraison.
- **Zones** : polygones indicatifs — lagon plein = couvert, ambre pointillé = à venir, popup au tap ; cadrage auto sur les 6 zones.
- **Repli garanti** : sans réseau/CDN (ou hors-ligne), la carte stylisée d'origine sert de canevas — jamais d'écran vide ; `mountRealMap`/`mountZonesMap` sont inoffensifs sans Leaflet et se remontent proprement à chaque re-rendu du DOM.
- **PWA** : tuiles OSM en cache-first borné (~80 tuiles, cache `lagon-tiles`) — la carte s'ouvre vite en 2ᵉ session.
- QC : **suite11** (14 tests) — tracé, bornes géo de Saint-Martin, maths du pin (clamp, monotonic, milieux), guards sans `L`, overlay présents.

## Lot 12 — photos réelles des produits (Wikimedia Commons, sans clé API)

Les 19 produits embarquent une vraie photo au lieu de l'emoji seul :

- **Source** : [Wikimedia Commons](https://commons.wikimedia.org) — fichiers sous licence libre (CC0 / CC BY / CC BY-SA / domaine public), servis par le CDN `wikimedia.org` en 640–960 px ; aucune clé API, aucun droit à négocier.
- **Données** : `products.json` porte deux champs par produit — `ph` (URL de la photo) et `cr` (crédit). Les données embarquées de `index.html` portent les mêmes (cohérence testée).
- **Rendu** : cartes (`pcard`) et fiche produit affichent `<img loading="lazy" referrerpolicy="no-referrer">` en `object-fit:cover` ; la fiche ajoute un crédit discret « Photo : … » sous l'image.
- **Repli garanti** : photo absente ou en erreur réseau → retour automatique au dégradé + emoji d'origine (`imgFail`/`bigImgFail`), jamais d'image cassée. En rupture, la photo est estompée comme avant.
- **Espace boutique** : le formulaire a un champ « Photo (URL https) » (http refusé, vide = repli emoji) ; la liste affiche la photo en fond de vignette.
- QC : **suite12** (17 tests) — champs `ph`/`cr` présents et uniques, synchronisation products.json ↔ données embarquées, rendus cartes/fiche, replis d'erreur (objets factices), CSS `object-fit`.

## Lot 13 — bilingue FR/EN (sans build, sans recharge)

Un sélecteur **Paramétrage → « Langue · Language »** (🇫🇷 Français / 🇬🇧 English) bascule toute l'interface :

- **Mécanisme** : le français est la langue source. `EN_DICT` traduit les textes exacts (chrome, sections, boutons, toasts, noms/formats/descriptions des 19 produits, catégories, sous-rayons, paniers, créneaux, moyens de paiement, zones, FAQ, promos, onboarding) ; `EN_PAT` traduit les phrases interpolées (stock, compteurs, ETA, « Encore X € pour la livraison offerte », « Ajouter au panier · 4,50 € »…) ; les nœuds composés « A · B · C » sont traduits segment par segment.
- **Sans toucher aux templates** : un `MutationObserver` traduit les nœuds ajoutés au fil des rendus (écrans, feuilles, toasts) ; les attributs `placeholder`/`aria-label`/`title` sont couverts. En JavaScriptCore (harnais de tests), l'observateur est simplement absent — les helpers `t`/`trText` restent testés directement.
- **Persistance** : la langue est stockée dans `lm-config` (à côté des frais/seuil/WhatsApp) ; l'app rouvre dans la langue choisie, `<html lang>` suit.
- **Produits** : priorité à la variante du commerçant (`n_en`/`d_en`, éditables dans l'Espace boutique) sinon dictionnaire intégré, sinon français — jamais de texte manquant.
- QC : **suite13** (36 tests) — cœur de traduction, 15+ patterns, composites, couverture complète du dictionnaire (produits, badges, catégories, créneaux, FAQ, promos…), replis FR, rendu EN réel, persistance et préservation des autres réglages.

## Lot 17 — import facture / devis (scan → approbation 1 par 1)

Peupler le catalogue depuis les documents papier du fournisseur, avec **validation humaine de chaque produit** :

**Scan → coller → analyser → approuver un par un → publier**

1. Scannez la facture ou le devis (iPhone : appareil photo → **Live Text** → copier le texte ; ou tout OCR)
2. **Espace boutique → « 🧾 Import facture / devis »** → collez le texte → **🔍 Analyser le texte**
3. Chaque ligne exploitable devient une **proposition** (nouveau produit ou mise à jour si l'id existe déjà)
4. Les propositions s'approuvent **une par une** : nom, prix, stock, emoji, catégorie (déduite par mots-clés) et sous-catégorie sont éditables avant validation — ✓ Approuver ou ✕ Rejeter, puis le suivant (« Produit 1 sur N »)
5. Les approuvés rejoignent « Catalogue en cours » (et la file survit à un rechargement) → publication habituelle : **products.json** ou **🚀 Backend**

**Ce que l'analyse comprend** : une ligne par produit, prix en fin de ligne (`7,90`, `3,95 €`), quantité en préfixe (`2`, `x3`), format en suffixe (`200 G`, `1,5L` → rangé dans le champ `f`), lignes de bruit ignorées (Total, TVA, Net à payer, adresse, date…), dédoublonnage au sein de la fournée, catégorie + emoji devinés (fruits, boulangerie, crèmerie, poissonnerie, boucherie, boissons, surgelés, épicerie — repli : épicerie/🛒).

Exemple de texte reconnu :
```
2 KG TOMATES GRAPPE 7,90
BRIE AOP 200 G 3,95 €
1 BAGUETTE TRADITION 1,20
MAHI MAHI FILET KG 18,50
```

QC : **admin17** (15 tests) — extraction/prix/noms/formats/catégories, bruit ignoré, lignes sans prix rejetées, doublons détectés (mise à jour) et dédoublonnés, file persistée, approbation (ajout + avancement), refus prix invalide, rejet, remise à zéro.

## Lot 16 — sécurisation : Supabase Auth, écritures restreintes au marchand

Fin du mode prototype : la clé anon ne peut plus rien écrire dans `products` ni lire les commandes.

| Action | Qui peut |
|---|---|
| Lire le catalogue (`products`) | tout le monde (clé anon) — l'app client n'a jamais besoin de compte |
| Publier / modifier le catalogue | **uniquement le marchand authentifié** (session Supabase Auth de l'Espace boutique) |
| Créer une commande (`orders`) | les clients, anonymes |
| Lire les commandes | **uniquement le marchand authentifié** |

**Activation (une fois)** :

1. Dans Supabase, **SQL Editor** : ré-exécutez [supabase-schema.sql](supabase-schema.sql) — il est idempotent et remplace les policies permissives du Lot 15 par les policies restreintes.
2. Créez le compte marchand : **Authentication → Users → Add user → Create new user** (email + mot de passe, cochez **Auto Confirm User**).
3. Dans l'**Espace boutique** → carte **Compte marchand** : connectez-vous avec cet email/mot de passe.

Au quotidien : ouvrez l'Espace boutique, connectez-vous (la session persiste et se rafraîchit toute seule — en cas d'expiration, un simple « Se déconnecter / Se connecter » suffit), puis « 🚀 Publier le catalogue vers le backend ».

QC : **admin16** (11 tests) — session persistée, refus de publication sans session, Bearer = jeton marchand vs clé anonyme, lecture publique anonyme, refresh automatique du jeton expiré + retry, échec de refresh → session nettoyée, logout.

## Lot 15 — backend optionnel (Supabase REST, sans SDK)

L'app gagne une vraie base en ligne **sans rien perdre du mode local** : tant qu'aucun backend n'est configuré, tout fonctionne comme avant (products.json + localStorage). Dès que l'URL et la clé anon d'un projet Supabase sont saisies, le catalogue et les commandes passent par la base.

**Mise en route (10 minutes, gratuit)** :

1. Créez un projet sur [supabase.com](https://supabase.com) (plan gratuit suffisant).
2. **SQL Editor → New query** : collez le contenu de [supabase-schema.sql](supabase-schema.sql) → **Run** (tables `products` et `orders` + règles d'accès).
3. **Settings → API** : copiez l'**URL du projet** et la clé **anon public** (jamais `service_role`).
4. Collez-les dans **l'app → Paramétrage → Backend (optionnel)** (ou dans **l'Espace boutique → Backend Supabase**) → « Tester la connexion ».
5. Dans l'Espace boutique : « 🚀 Publier le catalogue vers le backend » envoie tout le catalogue courant en un seul upsert. L'app lit alors ces produits au prochain cycle.

**Ce que ça change** :

| Flux | Sans backend | Avec backend |
|---|---|---|
| Catalogue | products.json (GitHub) | table `products` (repli auto sur products.json si le backend est injoignable) |
| Commandes | localStorage uniquement | POST dans la table `orders` — la confirmation ne s'affiche qu'après accord du serveur |
| Publication produits | télécharger products.json → GitHub | un bouton (upsert groupé), ou les deux |

⚠️ **Prototype** : les règles RLS du schéma sont volontairement permissives (clé anon = lecture produits + écriture commandes + publication catalogue). Avant une vraie exploitation, ajoutez Supabase Auth et restreignez les écritures.

QC : **suite15** (14 tests) — mappings `rowToProduct`/`appToRow`, en-têtes API, dispatcher `refreshCatalog` (API prioritaire, repli JSON vérifié), `payNow` sans backend / avec accord serveur / avec échec réseau, `testBackend`, restauration de config ; **admin15** (9 tests) — publication groupée, chargement backend, URL non https refusée, déconnexion.

## Lot 9 — alimenter le catalogue périodiquement (sans toucher au code)

La liste des produits disponibles vit dans [products.json](products.json), un simple fichier JSON à la racine. L'app le recharge automatiquement :

| Moment | Mécanisme |
|---|---|
| À l'ouverture de l'app | cache local (`lm-catalog`) affiché instantanément, puis `products.json` rechargé |
| Toutes les 5 minutes | timer `CAT_TTL` (5 min) |
| Au retour sur l'app (onglet réactivé) | `visibilitychange` si le cache est périmé |

Chaînage : **products.json (réseau) → cache localStorage → données embarquées** — jamais d'écran vide, même hors-ligne.

**Pour changer les produits (prix, stock, rupture, nouveau produit)** : modifiez `products.json` — y compris **directement sur github.com** (bouton crayon sur le fichier → Edit → Commit), la CI et Pages redéploient en ~1 minute, et l'app se met à jour au prochain cycle. Aucun code, aucun build, aucune clé API. Champs d'un produit : `id` (unique), `n` (nom), `b` (marque), `f` (format), `pr` (prix, nombre), `u` (prix au kg, chaîne), `e` (emoji de repli), `g` (2 dégradés de couleur), `cat`, `sub`, `bd` (badges), `st` (stock ; 0 = rupture), `d` (description), `promo` (facultatif), `ph` (URL https d'une photo, facultatif), `cr` (crédit photo, affiché sur la fiche).
